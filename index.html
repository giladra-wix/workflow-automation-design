Requirements

Functional

  • Browse a catalog of components and connect accounts (OAuth, API key or basic auth).
  • Build a workflow: one Trigger, then any mix of Decisions and Actions, with data mapped from earlier step outputs.
  • Publish, unpublish and version workflows.
  • Triggers: webhook, polling, schedule. Decisions: filter, branch, pause and resume.
  • Run history with step inputs and outputs; retry a failed run.
  • Agentic actions: a goal plus a set of allowed actions as tools, returning a validated result.

Non-functional

  • Never lose a trigger event. At-least-once delivery with idempotency keys, so side effects happen effectively once.
  • One heavy tenant or slow provider must not affect others.
  • Respect each provider's rate limits.
  • 99.95% availability for accepting trigger events. For webhooks, p99 of under 5 seconds from receipt to the first step starting.
  • Encrypted credentials; sandboxed custom code.
  • Agents stay within their permissions and their cost, call and time limits, even when a tool result tries to mislead them.

Architecture

Trigger sources write events to Kafka. The orchestrator moves each run forward one step at a time. All connector code, including the poll handlers that pollers run, executes in one sandboxed runtime pool, which is the only caller of provider APIs. The Connection Service talks only to providers' OAuth endpoints, for token exchange and refresh. All outbound traffic leaves through the egress proxy. Agent actions run in the Agent Runtime, which owns the model loop and the policy gate and calls tools through the Connector Runtime. To the orchestrator, an agent is one action.

The path of one event

  1. A trigger source (webhook, poll or schedule) emits a TriggerEvent to trigger-events, with a deterministic eventId.
  2. The orchestrator creates the run only if run_by_event accepts the conditional insert, then enqueues the first step on step-tasks.
  3. The Connector Runtime loads the pinned bundle, decrypts the token with the account DEK, and calls the provider through the egress proxy.
  4. The step result goes to run-commands, keyed by runId. Partition ownership makes one orchestrator instance the owner of the run, and a version check on each write keeps the transition exact.
  5. Delays and waits put the run to sleep as a timer or correlation row. TimerFired or EventMatched wakes it through the same topic.
  6. An agent action is dispatched like any other action, to the Agent Runtime. It runs the model loop, sends each allowed tool call through step-tasks, and reports one StepCompleted when it finishes.

Control plane

Connector Registry

Each connector is a versioned manifest plus a small code module built with a connector SDK. The manifest declares the auth type, the triggers (webhook or polling), the actions, and an input and output JSON Schema for each. The builder renders its forms from those schemas. Connectors deploy independently, so a broken Gmail connector can't take down the engine.

Workflow Service

A workflow is a tree of steps stored as JSON: a trigger, then an ordered list of steps, where a branch holds its own list of steps for each path. Step inputs reference the trigger and earlier steps with templates.

{
  "schemaVersion": 1,
  "trigger": { "id": "trigger", "connector": "salesforce", "event": "new_lead",
               "connectionId": "c_sf_01", "config": { "object": "Lead" } },
  "steps": [
    { "id": "check_score", "type": "decision", "kind": "filter",
      "condition": { "left": "{{trigger.Lead_Score__c}}", "op": "gt", "right": 80 } },
    { "id": "welcome", "type": "action", "executor": "connector", "connector": "whatsapp",
      "operation": "send_message", "connectionId": "c_wa_01",
      "input": { "to": "{{trigger.Phone}}", "text": "Hi {{trigger.FirstName}}" } }
  ],
  "settings": { "timezone": "Asia/Jerusalem", "autoPauseAfterFailures": 10,
                "onError": { "retry": { "maxAttempts": 5, "backoff": "exponential" }, "then": "fail_run" } }
}

After the trigger there are only two step types, matching the product's components. An action does work, and its executor is connector, code or agent. A decision controls the flow, and its kind is filter, branch (paths with conditions, plus a default), delay or wait_for_event. Because branches nest their own steps, the structure can't contain a cycle, and the steps a field may reference are simply the ones above it on its path.

  • Immutable versions. Publishing creates a new version, and each run is pinned to the version it started on. Editing never breaks runs in progress.
  • Publishing. One Postgres transaction inserts the next version, moves its trigger_subscriptions to that version and sets active_version. After it commits, the trigger is activated: a webhook is registered with the provider through the runtime, a poll schedule is created in poll_state, or the first timer is written. Unpublishing reverses this, and runs still waiting are cancelled.
  • Validation at publish: unique step ids, each reference points to a step above it on its path, required fields mapped, mapped types fit the schemas, connections active and owned by the account, agent tools allowed and their constraints valid.

Connection Service

  • Tokens use envelope encryption with the account's DEK (see Integrations & credentials).
  • It is the only writer of tokens. A background job refreshes OAuth tokens before they expire, and a per-connection lock stops two refreshes from racing.
  • The runtime host decrypts a token only at execution time and keeps it in memory only.
  • A revoked token flags every workflow that uses the connection and notifies the user.

Actions

An action is an entry in its connector's manifest. Simple calls are fully declarative. Calls that need logic, such as pagination, lookups or reshaping a response, name a code handler instead of a request.

- key: send_channel_message
  displayName: Send Channel Message
  sideEffect: true
  idempotency: { supported: true, header: X-Idempotency-Key }
  input:
    type: object
    required: [channel, text]
    properties:
      channel: { type: string, title: Channel, dynamicOptions: options/channels }
      text:    { type: string, title: Message }
  request:                                   # declarative: no code needed
    method: POST
    path: /api/chat.postMessage
    body: { channel: "{{input.channel}}", text: "{{input.text}}" }
  output:
    type: object
    properties: { ts: { type: string }, channel: { type: string } }
  sample: { ts: "1728885607.000100", channel: "C04SALES" }
// handler-backed action
export async function findLead(ctx: Ctx, input: { email: string }) {
  const q = `SELECT Id, Email, Lead_Score__c FROM Lead WHERE Email = '${ctx.escape(input.email)}' LIMIT 1`;
  const res = await ctx.http.get("/services/data/v61.0/query", { params: { q } });
  return res.data.records[0] ?? null;
}

In a workflow, an action with executor: connector picks the connector, operation and connectionId and maps its input with templates. The Workflow Service validates the mapping at publish against the input schema of the pinned connector version. Code actions (executor: code, run in the sandbox) and agent actions (executor: agent, run by the Agent Runtime) follow the same contract: mapped input, one task, one validated result.

Execution inside the Connector Runtime

  1. Take the task {runId, stepId, attempt} from step-tasks.
  2. Load the pinned workflow version, which is cached since it never changes, and the connector bundle by hash.
  3. Resolve templates from the trigger and step outputs, then validate the input against its schema.
  4. Take a rate-limit token for the connection and for the provider app. If none is available, re-queue with a delay.
  5. Claim action_ledger (runId, stepId). If it's already done, return the stored result.
  6. Run the request or handler in the sandbox. The host adds the Authorization header and the idempotency key.
  7. Classify the response with the manifest's errors: success, retryable, auth (refresh once), or fatal.
  8. Validate the output against its schema. Anything over 256 KB goes to S3.
  9. Write step_executions, mark the ledger done, send StepCompleted to run-commands, and acknowledge the task.

Agentic actions

An agentic action gets a goal instead of one fixed operation, and chooses from a set of allowed actions as tools. To the workflow engine it is still an action: it receives input, does work, keeps state while it runs, and returns output that later steps can map. It is defined as an action with executor: agent, and the Agent Runtime runs it. Example: Agent: Resolve Customer Request may call Salesforce: Find Customer, Shopify: Get Order and Gmail: Send Reply before it returns.

Defining an agent action

{
  "id": "resolve_request",
  "type": "action",
  "executor": "agent",
  "model": "claude-sonnet-5-5",
  "goal": "Resolve this customer request: {{trigger.body}}. Customer email: {{trigger.from}}.",
  "instructions": "Look up the customer and their latest order before replying. Reply once.",
  "tools": [
    { "connector": "salesforce", "operation": "find_customer", "connectionId": "c_sf_01" },
    { "connector": "shopify",    "operation": "get_order",     "connectionId": "c_shop_01" },
    { "connector": "gmail",      "operation": "send_reply",    "connectionId": "c_gm_01",
      "fixed":  { "to": "{{trigger.from}}", "threadId": "{{trigger.threadId}}" },
      "policy": { "maxCalls": 1, "approval": "none" } }
  ],
  "limits": { "maxTurns": 12, "maxToolCalls": 10, "maxTokens": 200000,
              "maxCostUsd": 0.50, "timeoutSec": 300 },
  "output": {
    "type": "object",
    "required": ["status", "summary"],
    "properties": {
      "status":  { "enum": ["resolved", "needs_human"] },
      "summary": { "type": "string" },
      "orderId": { "type": "string" }
    }
  }
}

Later steps use the result like any other action, for example a branch on {{steps.resolve_request.output.status}} that routes needs_human to a Slack alert.

A tool call executes through exactly the same pipeline as an action step: template and input validation, rate limits, the action_ledger claim, credentials added by the runtime host, error classification and output validation. The model asks for a call; the platform decides whether it runs and runs it.

How the agent loop runs

To the orchestrator, an agent is one action: it dispatches the task once and waits for one StepCompleted. The loop runs inside the Agent Runtime, which is built the same way as the orchestrator: its commands arrive on agent-commands keyed by session, one instance owns each session, and every change is a conditional write on agent_sessions with an outbox. The policy gate and the model workers are parts of the Agent Runtime. Each model turn and each tool call is its own durable unit, so an agent can run for minutes, wait for an approval, or survive a crash without losing its place.

  1. Start. The orchestrator dispatches the agent action on step-tasks. The Agent Runtime replies Accepted, so the run's step waits without a queue timeout. It creates the agent_sessions row with the limits snapshot and the tool specs generated at publish, and enqueues turn 1 on agent-llm.
  2. Model turn. A model worker sends the transcript and tool specs to the model, stores the response in agent_events before anything acts on it, and reports TurnCompleted on agent-commands.
  3. Policy gate. Each requested call is checked: is the tool allowed, are the arguments valid and within constraints, is any limit reached, does it need approval? Rejected calls go back to the model as an error result, so it can try another way.
  4. Tool calls. Allowed calls go on step-tasks with deterministic ids such as R1:resolve_request:t2:c1, with replies addressed to agent-commands. Each one writes its own child step_executions row, so it shows in the run timeline and counts toward billing.
  5. Next turn. When all calls of the turn have their results, they are appended to the transcript and the next turn is enqueued.
  6. Finish. The model ends by calling a built-in finish tool whose schema is the action's output. The Agent Runtime validates it and sends one StepCompleted to run-commands. The orchestrator writes the output and moves the run on.

Tool-call history, retries and replay

  • Recorded responses are never asked again. The model worker writes each response with a conditional insert keyed by session and turn, and checks for a stored response before calling the model. After a crash, the Agent Runtime rebuilds the session from agent_events. A turn whose model response is already stored is replayed from storage, so a non-deterministic model can't take a different path the second time.
  • Tool calls are idempotent. Deterministic call ids go through action_ledger, so a redelivered call can't send the same email twice.
  • Retries. A model API error (429, 5xx) retries that turn with backoff. A tool's retryable error retries that call. Neither restarts the whole session.
  • Audit and debugging. The run view shows the full transcript: each model turn, every proposed call, what the gate allowed or rejected and why, approvals, and every result.
  • Billing. The agent action is one task, each tool call that succeeds is one more, and model tokens are metered on top.

Every trigger emits TriggerEvent {workflowId, version, eventId, payload}. The eventId is the dedup key downstream.

Leases

Pollers, timer scanners and the token refresher all divide their work into 1024 shards. Each shard has one owner at a time, held as a Redis lease with a short TTL that the owner renews every few seconds. If an owner dies, its leases expire and another instance takes the shard.

  • Fencing, for pollers. When a poller takes a shard it increments that shard's epoch in Postgres (shard_epochs). Every cursor write in poll_state carries that epoch and is rejected if a newer owner exists, so a paused or partitioned old owner can't move a cursor backwards. The epoch lives in the same database as the cursor, so the check is part of the same write.
  • No fencing needed elsewhere. Timer scanners write to DynamoDB, where their duplicates are already harmless: the event id is deterministic, deleting a timer twice does nothing, and the next timer has a deterministic id. The token refresher is protected by its per-connection lock and a last_refreshed_at check before saving.
  • Why Redis is enough. A Redis failover can briefly give a shard two owners. That only costs duplicate work: the epoch check protects poll cursors, and run_by_event drops duplicate events.
  • The orchestrator needs none of this. Kafka partition ownership on run-commands decides which instance owns a run, and the rev check fences its writes. The Agent Runtime works the same way on agent-commands, keyed by session and fenced by agent_sessions.rev.

Trigger to execution

Every trigger type starts differently but ends the same way. Each one turns something that happened into a TriggerEvent with a deterministic eventId and writes it to Kafka. From there, one shared path turns the event into exactly one run.

The shared path: event to run

  1. Consume. The orchestrator instance that owns the trigger-events partition for workflowId reads the event.
  2. Check the workflow. If the workflow is paused or archived, the event is dropped and logged. The event carries the version its subscription was created for, so an event already in flight during a republish still runs on that version.
  3. Check limits. At its concurrency limit, the workflow still gets its run, created as pending and started when a slot frees. Over its monthly task quota, the account gets no run; the event is logged and the owner is notified.
  4. Claim the event. Conditional insert into run_by_event on workflow_id#event_id. If the row exists, this is a duplicate and processing stops here.
  5. Create the run. One TransactWriteItems writes the runs row (status running, or pending at the concurrency limit, rev = 1, payload reference in S3), the first step_executions row as pending, and an outbox message for the first step.
  6. Hand off. The outbox relay publishes the first step to step-tasks, and the orchestrator commits its Kafka offset. From here the run follows the execution flow.

When the write to Kafka fails

  • Webhook. Ingress returns 503, and the provider's own retry delivers the event later. Ingress never returns 200 for an event it hasn't stored.
  • Polling. The cursor isn't advanced, so the next poll fetches the same records again and dedup removes any that did get through.
  • Schedule. The timer row stays in place, so the next scan finds it and emits it again. The deterministic eventId makes the retry harmless.

Execution flow

The orchestrator moves a run forward one step at a time. A run keeps a cursor, its position in the definition tree written as a path of step ids such as by_value.default.wait_3d, and a context: the trigger output plus every finished step's output.

After the trigger, a workflow has two kinds of step. An action does work outside the run and is dispatched to an executor. A decision only decides what the run does next, and the orchestrator evaluates it itself.

Decisions that don't wait are evaluated inline, so one command can carry a run through several filters and branches and stop only at the next action or wait. Each decision's outcome is recorded on its own step row, for example { "outcome": "take", "path": "default" }. Steps on paths a branch didn't take get no row at all: the run view shows them as skipped, derived from that outcome and the compiled definition. That keeps every transition's transaction small, under DynamoDB's 100-item limit however large a branch is.

Long-running actions. An executor can reply Accepted for work that outlasts a queue's visibility timeout, such as an agent waiting for an approval or a provider job that finishes later. The step then waits under its own deadline, which the executor extends with heartbeats, until StepCompleted arrives.

Each transition is one conditional write: the runs row checked against its rev, plus the step row, timer and outbox message in the same transaction. An outbox relay reads new outbox rows from DynamoDB Streams and publishes them to their queues, so a message is sent if and only if its transition was saved. Templates such as {{steps.create_task.output.Id}} are resolved by the executor when the step runs, from stored step outputs, so a run that sleeps for days still has everything it needs.

Queues, retries & recovery

Two kinds of queue, each used for what it does best. Kafka topics carry events and commands, where ordering and partition ownership matter. SQS work queues carry tasks for workers, where per-task visibility timeouts, delayed redelivery and thousands of small per-connector queues matter.

Workers and retries

  • Visibility timeout. A worker holds a task for the step's time limit plus a margin and acknowledges it only after the result is on run-commands. If the worker dies, the task becomes visible again.
  • Classification. The manifest's errors section marks responses as retryable (429, 5xx, timeout), auth, or fatal.
  • Backoff without sleeping. The orchestrator writes a timer for next_retry_at (exponential with jitter, honoring Retry-After). When it fires, attempt N+1 runs as a new step_executions row.
  • Out of retries. The step's onError policy applies: fail_run or continue.
  • Agent turns. A model API error (429, 5xx, timeout) retries that one turn with backoff, and a tool error retries that one call. Neither restarts the session.

Integrations & credentials

  • Connectors. Each provider is a versioned manifest plus a signed, content-addressed code bundle in S3. Every workflow version pins the connector versions it was published with.
  • Connecting an account. OAuth2 uses the authorization code flow with PKCE through the platform's OAuth app for that provider. API keys and basic auth are form fields. The Connection Service runs a test call to confirm the connection works.
  • Storage. Envelope encryption: a token is encrypted with the account's DEK. The DEK is wrapped by the region's KMS key with account_id as encryption context. There are a few KMS keys per region, not one per account, and dedicated keys only for enterprise customers who bring their own. The database holds only ciphertext, and deleting an account's wrapped DEK makes all its secrets unreadable.
  • Platform secrets. OAuth app client secrets, model provider API keys and app-level webhook secrets live in Secrets Manager. Each is readable only by the one service that needs it. Infrastructure access uses IAM authentication where it exists, so most services hold no password at all.
  • Webhook signing secrets. Per subscription, encrypted with the account's DEK like any user secret. Besides the runtime host and the Connection Service, Webhook Ingress is the only service allowed to decrypt, and only these secrets, which it caches for a few minutes.
  • Use at runtime. Workers prove their identity to KMS through workload identity (IRSA) and may only call Decrypt, with account_id as the encryption context. The runtime host adds the Authorization header outside the sandbox, so connector code never sees a token.
  • Refresh. The Connection Service is the only writer of tokens. It refreshes ahead of expiry and takes a per-connection lock when a worker reports a 401. invalid_grant marks the connection revoked and pauses the workflows that use it.
  • Provider limits. Token buckets per connection and per OAuth app, and queues per connector, so a slow provider affects only its own work.
  • Webhooks. Registered and removed automatically on publish and unpublish. A renewal job handles subscriptions that expire, and a reconcile job re-creates any that go missing.
  • Model provider. Model workers call the model API through the egress proxy with a platform key that never enters a sandbox. Prompts carry one tenant's data only, under provider terms that exclude training on it and with zero retention where offered. Tool results are cut to the action's output schema before they reach the model.

Isolation & fairness

  • trigger-events is partitioned by workflowId, which keeps per-workflow ordering and concurrency limits in one place. run-commands is partitioned by runId, so a busy workflow's runs spread across all orchestrator instances.
  • Separate step queues per plan tier and per connector. A slow Salesforce API only holds up Salesforce tasks.
  • Redis token buckets per connection and per provider app, matched to provider quotas. A task without a token is re-queued with a delay instead of holding a worker.
  • Weighted fair scheduling per tenant, so a burst of 1M events from one user can't starve others.
  • A task counter enforces plan quotas. One billable task is one successful action, whatever its executor, or one successful agent tool call.
  • Agents get their own limits: a monthly token and cost budget per account, a cap on concurrent agent sessions per tenant, and agent-llm queues per plan tier, since one session can hold capacity for minutes.

Regions and availability

  • Home region per account. Each account lives in one region, which also covers data residency such as EU-only. A region runs the full stack: ingress, Kafka, SQS, workers, Postgres, DynamoDB and S3.
  • Routing. Webhook URLs and API calls carry the region, for example hooks.eu.platform.com, so events land where their runs live and never cross regions.
  • Within a region. Every component runs across three availability zones. Losing one zone loses no data and needs no manual action.
  • Disaster recovery. Postgres replicas and DynamoDB global tables in a paired region, with point-in-time recovery for both. Kafka topics are mirrored and S3 buckets replicated to the same paired region. Writes are only ever made in the home region, which keeps conditional writes correct. Failing over moves an account's home region; consumers resume from mirrored offsets, and run_by_event drops any event processed twice across the switch.

Data model

Four entities hold the core of the platform, and agent steps add two more (below). A workflow is what the user edits. A workflow version is an immutable snapshot of it, made at publish. Each trigger event creates a run (an execution) pinned to one version, and a run has one step execution row per attempt of each step.

PK primary key · FK foreign key · UQ unique (enforced through the run_by_event conditional insert). Inputs and outputs over 256 KB move to S3 and the row keeps a *_ref.

Agent steps

An agent action adds two tables next to its step_executions row, both written by the Agent Runtime. agent_sessions holds one row per attempt with status, counters and the limits snapshot, and agent_events holds the ordered history of model turns, tool calls, gate decisions and approvals. Each tool call is also a child step_executions row with an id such as resolve_request.t2.c1, so it appears in the run timeline. Details are in Agentic actions.

Rules that keep the model consistent

  • Versions are immutable. Edits change only workflows.draft_definition. Publishing validates the draft and inserts the next workflow_versions row in the same transaction that updates active_version.
  • A run never changes version. runs.workflow_version is set at creation, so a run that sleeps for days still finishes on the definition it started with.
  • Step ids come from the definition. step_executions.step_id matches a step id in the pinned version, which is how the UI lines up the timeline with the workflow it ran.
  • Only the run's owner writes it. Each runs update checks and increments rev, and the step row, timer and outbox message are written in the same TransactWriteItems.
  • Billing comes from steps. billed_tasks counts the actions of every executor and the agent tool calls that succeeded. Model tokens are metered separately from agent_sessions counters. Filters, delays and filtered runs are free.
  • Retention follows the plan. runs, step_executions, agent_sessions and agent_events carry a TTL from accounts.retention_days. A version can be purged only when no run that has not finished still points at it.

Concrete flows

Four flows end to end. Each diagram shows which component owns each step. Dashed arrows are responses.

1. Webhook flow

Stripe: Payment Succeeded→Salesforce: Update Opportunity
  • Store first, then answer. Ingress returns 200 only after Kafka acknowledges the event. If Kafka is unavailable it returns 503, and Stripe's own retry delivers the event later.
  • Ingress does no workflow work. It routes, verifies and enqueues, so it stays fast and stateless. A slow Salesforce can never make Stripe time out.
  • Duplicates end at one place. Stripe retries arrive with the same evt_ id, so the eventId is the same, and the conditional insert into run_by_event drops them.
  • The orchestrator never calls a provider. It decides; the Connector Runtime executes. Credentials are added by the runtime host, outside connector code.

2. Polling flow

Salesforce: New Lead→Lead Score > 80→WhatsApp: Send Message
  • Ownership by shard. The poller holds the lease for shard 17, so it's the only process polling sub_9. The cursor write carries the lease epoch, so a stale owner's write is rejected.
  • Read behind, then drop what was seen. The query starts 5 minutes behind the cursor to catch records that became visible late, and the seen-ID set removes the overlap.
  • The order makes crashes safe. Events reach Kafka before the seen-ID write and the cursor move. A crash in between re-emits, and run_by_event drops the duplicate.
  • The filter runs in the orchestrator. A decision is a pure check over the run context, with no queue and no worker. A run that fails the filter ends filtered and isn't billed.

3. Delayed and branching flow

  • The decision is saved, not repeated. The branch's outcome, take(default), is recorded on its step row and the cursor sits on that path; vip's steps have no rows and show as skipped. Waking up continues that path; it doesn't evaluate the first branch again.
  • Fresh data after a wait. The second decision uses a get_order call made after the wait, because the trigger's data is 3 days old.
  • Waiting costs only storage. Nothing holds the run while it sleeps. Any orchestrator instance that owns R9's partition when the timer fires can continue it.
  • Changes during the wait. An edit publishes a new version, but R9 stays on its pinned version. An unpublish cancels the timer and marks the run cancelled. A duplicate TimerFired is ignored because R9 is no longer waiting on wait_3d.

4. Agentic action flow

Gmail: New Support Email→Agent: Resolve Customer Request→Branch: needs_human?→Slack: Alert
  • The model proposes; the platform decides. Every call passes the policy gate, which checks the allowlist, arguments, per-tool limits and approvals before anything runs. The rejected second reply in turn 4 is an example.
  • Tools are ordinary actions. Each allowed call runs through the same Connector Runtime pipeline as a normal step, with its own step_executions row, ledger claim and billed task.
  • Every turn is durable. Model responses are saved before they're acted on. After a crash the session is rebuilt from agent_events and stored responses are replayed, never requested again.
  • It ends like any action. The orchestrator dispatched one action and received one StepCompleted. The finish output is validated against the action's schema, and the next step branches on {{steps.resolve_request.output.status}}.
